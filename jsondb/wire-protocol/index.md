# jsondb wire protocol

The contract between a jsondb server and any client written against it. It is
the specification a driver implements; [`openapi.yaml`](../openapi.yaml) is the
machine-readable companion covering request and response *shapes*.

**This document exists for the semantics, which the shapes cannot express.** A
competent implementer can infer that `POST /api/v1/{coll}/_updateOne` takes a
filter and an update. Nothing in the endpoint shape reveals that `$inc` on a
string is an error rather than a coercion, that an upsert seeds only from
equality conditions, or that `{"tags": "x"}` matches `["x", "y"]`. Those are
below, and a driver that documents them wrongly will mislead its users.

---

## Versioning

Every data endpoint sits under `/api/v1/`. The number is the **API version**,
which moves independently of the server's build version.

- **Additive changes keep the version**: a new endpoint, a new response field,
  a new error `code`. Clients must ignore response fields they do not know.
- **Anything that could break a client written against the current contract
  requires a new version**, served alongside the old for as long as the old is
  supported.

`GET /api/v1/_version` reports both numbers and is the intended connect check —
it is the cheapest endpoint and proves the server speaks a contract the client
understands.

```json
{ "apiVersion": 1, "version": "v0.1.0", "revision": "abc123", "go": "go1.25.4" }
```

A client should compare `apiVersion` against its own and fail with both numbers
named. Requests to the unversioned `/api/…` paths return `404` with code
`wrong_api_version` and a message pointing at the prefix, rather than a bare
404 that looks like a missing collection.

## Connection URI

```
jsondb://host:port     plain HTTP
jsondbs://host:port    HTTPS
http:// or https://    accepted directly
```

There is **no `authSource` and no database in the path**. jsondb has a single
namespace — one file, collections as a column — so there is nothing for either
to select between. A URI carrying credentials, a path, or query parameters is
**rejected with an explanation**, not quietly accepted: silently dropping the
part a client cannot honour would look like it had worked.

There is no authentication yet. Everything below is available to anyone who can
reach the port.

## Errors

Non-2xx responses carry:

```json
{ "error": "human readable message", "code": "stable_slug" }
```

The `code` is the stable part and is what a driver maps to its error type. The
message is for humans and may change.

| Code | Status | Meaning |
| --- | --- | --- |
| `not_found` | 404 | No such document, index, or route |
| `invalid_filter` | 400 | Malformed filter, unknown query operator, bad path |
| `invalid_json` | 400 | Body was not valid JSON |
| `invalid_name` | 400 | Collection name outside `[A-Za-z0-9_-]+` |
| `invalid_update` | 400 | Malformed update document, or a type conflict |
| `duplicate_key` | 409 | Unique index violated |
| `wrong_api_version` | 404 | Unversioned path |
| `internal` | 500 | Anything else |

Matching on message text is not supported. New codes may appear without an API
version bump, so treat an unrecognised code as a generic failure carrying the
message.

## Semantics a driver must document correctly

### Documents and identity

`_id` is a **UUIDv7 string**, generated by the server and mirrored into the
document body on every write. It is not an ObjectId. Clients never set it: it
is stripped from replacement documents and rejected in update operators.

Numbers are JSON numbers, decoded as float64. Integers beyond float64's exact
range lose precision. There is no BSON type system — no `Date`, `Decimal128`,
`ObjectId` or `Binary`.

### Implicit array matching

A filter on a path matches when the value equals it **or**, if the value is an
array, when any element does.

```
{"tags": "x"}  matches  {"tags": "x"}  and  {"tags": ["x","y"]}
```

Comparisons traverse the same way: `{"vals": {"$gt": 8}}` matches when any
element exceeds 8. `$ne` and `$nin` mean **no** value matches, so a document
whose array contains the value is excluded, and a document missing the field
entirely is included.

**Objects are not arrays.** A document with `{"tags": {"x": 1}}` is not matched
by `{"tags": 1}`; only real arrays are traversed.

### Query operators

`$eq` `$ne` `$gt` `$gte` `$lt` `$lte` `$in` `$nin` `$like` `$regex` `$exists`
`$type` `$size` `$mod` `$all` `$elemMatch` `$not`, and top-level `$and` `$or`
`$nor`. Unknown operators are **rejected**, never ignored.

- `$regex` is Go's `regexp`, not PCRE. `$options` accepts `i`, `m`, `s`; any
  other letter is refused rather than dropped, because a silently ignored flag
  changes which documents match. A non-string value simply does not match.
- `$type` speaks JSON, not BSON: `string`, `number`, `int`, `double`, `bool`,
  `object`, `array`, `null`. BSON-only names (`binData`, `objectId`, `date`)
  are refused rather than silently never matching.
- `$size` matches arrays only, so `{"$size": 0}` finds empty arrays, not
  missing fields.
- `$not` and `$nor` **match documents that lack the field**, as in MongoDB.
- `$elemMatch` requires a *single* element to satisfy all criteria — which is
  not the same as two separate conditions on the same array.
- `$like` is a jsondb extension (SQL `LIKE`); MongoDB clients will not send it.

### Updates

An update document contains only operators; mixing operators with plain fields
is rejected, and replacing a whole document is `_replaceOne`.

`$set` `$unset` `$inc` `$mul` `$min` `$max` `$rename` `$currentDate` `$push`
`$pop` `$addToSet` `$pull` `$setOnInsert`.

- **Operators read the document as it was**, not each other's output, so the
  result never depends on application order. Two operators touching the same
  path are rejected as a conflict.
- **Type conflicts are errors, not coercions.** `$inc` on a string, or `$push`
  onto a number, returns `invalid_update` naming the path and how many
  documents conflict, and **nothing is written**.
- `$inc` on a missing field creates it with the increment; `$mul` on a missing
  field yields 0.
- `$currentDate` writes **unix epoch seconds** as an integer. There is no BSON
  `Date`. The `{"$type": …}` form is refused.
- `$rename` on a missing source is a no-op.
- `$pop` takes `1` (last) or `-1` (first).
- Any operator targeting `_id` is rejected.

### Results

```json
{ "matchedCount": 1, "modifiedCount": 0, "upsertedId": "…" }
```

**`matchedCount` and `modifiedCount` differ.** Matched counts documents the
filter selected; modified counts those whose stored bytes actually changed. An
update writing a document's existing values reports one matched and none
modified. Drivers must not present them as interchangeable.

`upsertedId` is present only when an upsert created a document.

### Upsert

When the filter matches nothing and `"upsert": true`:

1. The new document is seeded from the filter's **equality conditions only**.
   `{"tier": "gold"}` contributes `tier`; `{"age": {"$gt": 18}}` contributes
   nothing, because no single value is implied.
2. `$setOnInsert` fields are added.
3. The update's own operators are then applied to that new document — so
   `$inc` and `$push` behave on an insert exactly as they would on an existing
   document.

### Single-document operations

`_updateOne`, `_replaceOne` and `_deleteOne` act on the match with the **lowest
`_id`**. MongoDB picks an arbitrary match; jsondb's choice is defined, so
repeated calls walk a collection predictably.

### Indexes

`IndexSpec` is `{"paths": ["a", "b"], "unique": false, "name": "optional"}`.

- A compound index is **led by its first path**. It serves filters and sorts on
  that path and on the full key. SQLite may additionally skip-scan it for a
  trailing path when the leading path has few distinct values — a bonus, not a
  guarantee.
- **Unique indexes are sparse by default.** A document missing the path indexes
  as SQL NULL, NULLs are all distinct, so any number of documents may omit the
  path without colliding. This is MongoDB's *sparse* unique behaviour, not its
  default. Only documents carrying the path are constrained.
- Uniqueness is scoped to the collection.
- An index on `_id` is a no-op; it is already the primary key.
- Creating a unique index over data that already contains duplicates fails with
  `duplicate_key`.

### Collections

A collection is a column value, not a table. Consequences a driver should
surface:

- Collections are created implicitly on first write.
- **Dropping a collection that holds nothing is not an error** — "empty" and
  "does not exist" are the same state.
- **Renaming onto a name that already holds documents is refused** with
  `duplicate_key`, rather than silently merging two collections.
- `DELETE /api/v1/{coll}` drops documents *and* indexes. `_deleteMany` with an
  empty filter empties the collection but leaves indexes in place.

### Paging and cursors

`Find` returns a **complete array**, not a cursor. `limit` and `skip` are the
paging controls, and `skip` is O(skip) — deep paging over a large collection
gets progressively more expensive.

This is deliberate. The server pins a single SQLite connection, so a held
cursor would block every other query in the process. If streaming is added it
will arrive as a *new* endpoint and a new client method, never by changing what
`Find` returns — so a driver returning a slice today stays correct.

### Explain

`POST /api/v1/{coll}/_explain` takes the same arguments as a find and returns
the plan with its reading attached:

```json
{ "steps": [{"id": 4, "parent": 0, "detail": "SEARCH docs USING …"}],
  "seeksIndex": true, "sortsInMemory": false }
```

`seeksIndex` and `sortsInMemory` are computed **server-side and deliberately
so**. They are derived from SQLite's plan wording, which is an implementation
detail that has already changed once — when implicit array matching moved
indexed filters onto the multikey shadow table. A client deriving them by
matching on plan text would silently go wrong.

Two separate questions, not one: a sorted query can read in index order,
avoiding a sort, while reporting no constraint at all.

## Notes for driver authors

- **Ignore unknown response fields.** New ones may appear without a version
  bump.
- **Map on `code`, never on message text.**
- **Do not derive plan semantics client-side** — see Explain above.
- Filters and updates are opaque JSON as far as the wire is concerned; a driver
  need not validate them, and should let the server's `invalid_filter` and
  `invalid_update` errors through with their messages intact, since those name
  the offending path.
- The reference implementation is [`github.com/pmuston/jsondb-go`](https://github.com/pmuston/jsondb-go),
  whose parity with the storage library is enforced by a test in the server
  repository — the only place that can see both sides.
